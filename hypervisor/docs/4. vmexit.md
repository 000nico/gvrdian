after configuring properly the VMCS and VMXON region, and executing VMXON and VMLAUNCH succesfully, the next step is VM exits

certain exceptions have priority over vm exits. such as invalid opcodes, fault based on privilege level, gp exceptions based on checking i/o permission bits, among others.

the following instructions always cause VM Exits when executed in VMX Non-root:
  - cpuid
  - getsec
  - invd
  - xsetbv
  - invept
  - invvpid
  - seamcall
  - tdcall
  - vmcall
  - vmclear
  - vmlaunch
  - vmptrld
  - vmptrst
  - vmresume
  - vmxoff
  - vmxon

the following instructions cause VM Exits conditionally (depends on how did you seutp vmcs):
  - CTLS, ENCLS, ENQCMD, ENQCMDS, HLT, IN, INVLPG, INVPCID, LGDT, LIDT, LLDT, LR, SDGT, SIDT, SLDT, STR, LMSW, LOADIWKEY, MONITOR, MOV from CR3, MOV from CR8, MOV to cr0, MOV to cr3, MOV to cr4, MOV to cr8, MOV dr, MWAIT, PAUSE, PCONFIG, RDMSR, RDMSRLIST, RDPMC, RDRAND, RDSEED, RDTSC, RDTSCP, RSM, TPAUSE, UMWAIT, URDMSR, UWRMSR, VMREAD, VMWIRTE, WBINDVD, WBNOINVD, WRMSR, WRMSRNS, WRMSRLIST, XRSTORS, XSAVES

other cause of vm exits are 
  - exceptions, based on the exception bitmap. Also applies to exceptions generated by instructions such as INT3
  - external interrupts
  - non maskable interrupts
  - INIT signals
  - SIPIs
  - Task switches
  - System managmenet interrupts (SMIs)
  - VMX-preemption timer (you can configure a timer that triggers a VMEXIT when reaches 0, so you are sure that eventually your hypervisor will be executed)
  - Bus locks
  - Instruction timeouts

Some instructions changes behavior in vmx non-root, some of those are:
  - MOV from cr0, determined by CR0 guest/host mask and the cr0 read shadow
  - MOV from c3 if "enable EPT" vm-execution control is 1 and MOV from CR3 does not cause a VM Exit
  - MOV from CR4, determined by the CR4 guest/host mask and the CR4 read shadow
  - MOV from CR8 if does not cause a VM exit and modified by "use tpr shadow"
  - MOV to cr0 if doesnt cause a vm exit
  - MOV to cr3 if "enable PET" vm execution cotrol is 1 and does not cause a VM exit
  - MOV to cr4 if does not cause a vm exit
  - MOV to cr8
  - RMDMSR
  - RDTSC

among others. as you may probably already realized, these are a detection vector for detecting virtualized enviroments

why we NEED vm exit handlers?
because there are instructions that can be executed to know if a system is being virtualized, and we dont want the system to know, so, we need to intercept those to return arbitrary values. Instructinos such as CPUID in the bit 31 delatan if a hypervisor is present

how much vm exits need to be implemented?
depends on the goal. There are +70 exit reasons defined, but the majority of thin hypervisors dont impleement many, you will probably need
  - cpuid: mandatory
  - vmcall: communication guest and hypervisor
  - xsetbv: guest will do this at boot
  - ept violation: if using EPT
  - mov cr
  - hlt: to control when the guest sleeps
  - exceptions / nmi: when injecting exceptions
  - rmsr / wrmsr

the exit handler address need to be configured in vmcs
the exit handler should have an ASM stub that calls it, to save every register, call the exit handler and then restore the regs again
the exit handler should read the exit reason to VMREAD in order to know which instruction raised a VMEXIT
depending on the instruction, it should advance RIP

you can implement vmcall as your vm api, for communication with usermode
vm call only does one thing: trigger a vm exit with the proper reason registered
vm call does not have any operand, you define the arguments in rcx, rdx, r8, r9, rax (ret). the common thing is
  - rcx = opcode
  - rdx = arg 1
  - r8  = arg 2
  - r9  = arg 3
  - rax = return value
